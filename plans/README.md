## Direction options (maintainer's call, not queued work)

- **A. Make sources refreshable, and let the count escape the pane.**
  `InboxSourceResult` has `resolve` (write) but no re-read, so the pane editors
  leave open all day is frozen at mount. `Inbox.tsx` already hand-rolls an
  `onCount` callback to lift the total out of each section — exporting
  `useInboxCount(sources)` would let a navbar or dashboard widget show "3
  waiting" without rendering the pane. Additive and cheap now; breaking after
  1.0.
  **Update, 2026-09-14: the "let the count escape the pane" half is now
  planned** — Plan 016 (`plans/016-inbox-open-count-provider.md`) ships
  exactly this as `useInboxOpenCount()`, and Plan 017 builds a live navbar
  badge on top of it. The "make sources refreshable" half (a stale pane's
  own `Try again`/manual re-fetch) is **not** covered by either plan — it
  remains open, and overlaps with the existing "'Try again' is inert"
  finding below; a future plan could tackle both together.
- **B. Spike a data-first source descriptor before publishing.** `useItems` as
  a hook is why no source has a test — you need a renderer. Two of three
  sources are already just query + mapper. A `{query, params, toItem}` shape
  alongside the hook makes the common case pure and testable, with the hook as
  the escape hatch. Cost: two ways to declare a source. Scope as a spike.
  **Re-investigated, 2026-09-14 — premise no longer holds, downgraded to
  rejected.** This was true of the 3-source lineup on 2026-09-09. Checked
  against the current 4 built-in sources: `openTasks.ts` (241 lines) and
  `unpublishedDrafts.ts` (349 lines) are now both genuinely complex —
  multi-query joins, `assign`/`resolve`/`assess` mutations, addon-dataset
  reads — not "query + mapper." `todos.ts` (91 lines) has no GROQ query at
  all (a client-side store, not a fetch), so a `{query, params, toItem}`
  shape doesn't describe it either. Only `upcomingReleases.ts` (99 lines)
  still fits the simple shape today — one source out of four, not "two of
  three." The stated payoff ("makes *the common case* pure and testable")
  no longer matches which case is actually common in this codebase now.
  **Not recommending a spike.** Revisit only if a future built-in source is
  genuinely simple query+mapper shaped *and* there are enough of those to
  matter — a one-off shape for a single source isn't worth a second way to
  declare a source.
- **C. Snooze.** The store already compares timestamps and prunes by TTL, so
  "not now" is close to a predicate change. But it adds a second verb, which
  reopens the deliberate one-verb decision recorded in
  `SelectionActions.tsx:18-28`. Technical cost low, design cost real.
- **D. Bounding the Done view by recency.** Raised in review: Done accumulates,
  mainly for `unpublishedDrafts` (a closed task leaves its source query on
  reload; a dismissed draft does not). Note that a "remove from Done" action
  cannot shrink stored state — clearing the record returns the item to Open, so
  a third action would mean a new permanent flag. Showing only recently-done
  items is the cheaper answer and preserves the one-verb rule. Not obviously
  worth doing until it annoys someone in real use.

## Lifecycle investigation, 2026-09-13 (second run)

Prompted directly by the maintainer: "when it keeps on living and life keeps
on going... things get finished, some stay unfinished... we need to take
care of that." Scoped to the direction/lifecycle theme against commit
`32e028c`. This codebase already has *some* lifecycle awareness — dismissals
TTL out after 90 days (`DISMISSAL_TTL_DAYS`), snoozes self-prune once their
wake time passes — so the investigation looked for where that awareness is
inconsistent or missing, not for a lifecycle story from scratch.

- **A todo marked done can silently reappear after 90 days.** `todos` has no
  `resolve`, so "mark done" only ever dismisses it (`InboxSection.tsx:170-177`),
  and dismissals age out (`dismissals.ts:25`) — a deliberate nudge for
  content sources (an ancient still-unpublished draft *should* resurface),
  but wrong for a todo, which has no other way to become "not done" again.
  `todos.ts`'s own `withoutTodo` doc comment already names this exact
  tension. **This is a correctness bug, not a direction option** → **Plan
  014**.
- **No cleanup path for departed editors' state.** `structureInbox.dismissals/
  snoozes/todos.<userId>` documents live in the customer's dataset forever;
  nothing ever deletes one, and there's no plugin-provided or documented way
  to find a departed teammate's leftover documents as team composition
  changes over a project's life. Distinct from the existing "Privacy note"
  finding below (that one is about *readability* of an *active* editor's
  state; this is *unbounded growth* from *departed* ones). → **Plan 015**
  (a pure diff helper + README recipe, same shape as `buildDigest` — not
  automated deletion).
- **Checked, not a finding**: a departed teammate's still-assigned draft/task
  already degrades gracefully — `assigneesById` is built from the *current*
  assignable-user list, so a stale `assignedTo` just falls back to the
  "Unassigned" placeholder rather than breaking. No action needed.
- **Direction D above ("Bounding the Done view by recency") — re-confirmed,
  downgraded further.** Its storage-level concern is already handled by the
  90-day dismissal TTL; what's left is only a UI nicety (hiding very old done
  items), not an unbounded-growth problem. The original "not obviously worth
  doing" verdict stands.
