## Why this matters

The release job holds this package's npm publish credentials and OIDC
provenance-signing rights, and it executes third-party code that is resolved
fresh from the registry at run time.

`npx semantic-release` is invoked in a job with `NPM_TOKEN` and
`id-token: write` in scope. Neither `semantic-release` nor
`@sanity/semantic-release-preset` appears in `devDependencies` or in
`package-lock.json`, so `npm clean-install` never installs them and `npx`
downloads an unpinned dependency tree at that moment. The `npm audit signatures`
step that runs immediately before checks only the lockfile-installed tree, so
the code that actually performs the publish is outside the integrity check that
appears to cover it.

A compromised release of `semantic-release` or any of its transitive
dependencies would run with the ability to publish this package under a
provenance attestation that says it came from this repository.

There is a second, more mundane consequence: `.releaserc.json` extends
`@sanity/semantic-release-preset`, which `npx semantic-release` does not
install. The first real release attempt will most likely fail to resolve it.

This is a regression against the maintainer's own convention, which makes the
fix low-risk: the sibling repos `sanity-plugin-link-checker` and
`sanity-plugin-cockpit` both declare `@sanity/semantic-release-preset` in
`devDependencies`. Match them.

## Steps

### Step 1: Add the release tooling as locked devDependencies

Run:

```
npm install --save-dev semantic-release @sanity/semantic-release-preset
```

Use whatever versions npm resolves — do not pin to a version you invent. If
`@sanity/semantic-release-preset` already brings `semantic-release` as a direct
dependency rather than a peer, installing both explicitly is still correct: it
is the top-level binary being invoked.

**Verify**: `grep -c 'node_modules/semantic-release"' package-lock.json` → ≥ 1,
and `node -e "const p=require('./package.json');console.log(Object.keys(p.devDependencies).filter(d=>/semantic|release/.test(d)))"`
→ lists both packages.

### Step 2: Stop the workflow resolving anything at run time

In `.github/workflows/main.yml`, change the release step from
`npx semantic-release` to `npx --no-install semantic-release`. The
`--no-install` flag makes `npx` fail loudly if the binary is not already in
`node_modules`, instead of silently fetching it — which is the entire point of
this change.

Leave the `if: always()` and the `env:` block exactly as they are.

**Verify**: `grep -n 'semantic-release' .github/workflows/main.yml` → shows
`npx --no-install semantic-release`.

### Step 3: Prove the config resolves

Run a dry run locally. It must not publish, tag, or push:

```
npx --no-install semantic-release --dry-run --no-ci
```

Expect it to load `@sanity/semantic-release-preset` and report what it *would*
do. Warnings about not being on a CI provider, or about no release being
necessary, are fine. A failure to **resolve the preset** is not — that is the
latent bug this plan also fixes, and it must be gone.

**Verify**: the command exits 0 and its output contains no
`Cannot find module '@sanity/semantic-release-preset'`.

### Step 4: Confirm nothing else broke

The new devDependencies pull in a large tree; make sure they did not disturb
the build.

**Verify**: `npx tsc --noEmit -p tsconfig.json` → exit 0; `npm run lint` →
exit 0; `npx vitest run` → all pass; `npm run build` → `[success]`.

## STOP conditions

Stop and report back if:

- The dry run tries to publish, push, or create a tag. It must not; if it does,
  the `--dry-run`/`--no-ci` flags are not taking effect — stop immediately.
- `@sanity/semantic-release-preset` cannot be installed (private registry,
  404). Report rather than substituting a different preset.
- Installing the tooling introduces a peer-dependency conflict that npm cannot
  resolve without `--force` or `--legacy-peer-deps`. Do not use either flag;
  report the conflict.
- The lockfile churns by thousands of unrelated lines — that suggests the
  install also upgraded something else. Report before committing.
